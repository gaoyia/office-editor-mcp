# apply 开始前固定 id

状态：⚠️ 只接上了一部分 op，见文末「审计发现的遗漏」。
日期：2026-10-30

不在三种格式的待做表里，不占待做序号。这是缺陷修复，记录见 `.bugfix-reports/2026年-10月-30日-⚠️-按位置编号的id在同一次apply里漂移.md`。

排在 2026-10-30 审计拆出的重构计划前面。

用户 2026-10-30 决定：apply 开始前，把所有 op 里的 id 按原文件解析成节点；后面的 op 不受前面增删的影响。

## 目标

一次 apply 里，每条 op 点名的对象，都是调用方 inspect 原文件时看到的那个对象。

- 被前面 op 删掉的对象，后面再点名时报 `IdNotFound`。
- 同一批里新建的对象，要等下一次 inspect 拿到 id 才能点名。

本份是第一期，只做已经实测出问题的两类：

- docx 段落类 id：`para:index:{n}`，以及页眉页脚、框内、注内、批注内的 `…/para:index:{k}`
- pptx `slide:{n}`，以及挂在它下面的所有 id

## 不做

- 不改 id 的字符串格式。
- 不改有内容编号的 id（`para:{paraId}`、`pic:{cNvPrId}`、`shape:{shapeId}` 等）。它们本来就不漂移。
- 第二期的其余位置 id 不在本份做，见文末。

### 1. 文档

- `docs/json-contract.md` 的「稳定 id」一节加一条：一次 apply 里，所有 id 都按 apply 开始时的文件解释。
  - 被前面 op 删掉的对象，后面再点名报 `IdNotFound`。
  - 同一批里新建的对象不能按位置点名。
- `docs/json-contract-docx.md` 第 18–19 行：「只够同一次 inspect 之后立刻 apply」改成指向上面这条。
- `docs/json-contract-pptx.md` 第 228 行：「按新顺序计」改成上面这条。
- 契约里所有写着 `after` / `start` 一类、引用别的对象的字段，同样按这条解释，在文档里点明。

### 2. 做法

2026-10-30 定下的做法：

- pptx：apply 开始时记下每页的 `p:sldId/@id`。增删移动之后重新列出页，但 `index` 改回开始时的页号。查找按这个页号，不按当时的位置。新页的页号记 0，不能被旧的 `slide:{n}` 点中。
- docx：部件第一次载入时，按 `find_p` 的同一套顺序给已有 `w:p` 写内存属性 `ooxp:pin`。文本框、注、批注各自从 1 起。写出时丢掉这个属性。本批新建的段落写成空 pin，不占用旧序号。
- create 用的是 `para:{paraId}` 和直接拼包，不在同一批里按位置点名新对象。产物不变。

约束有三条：

- 产物里不能留下任何痕迹。
- 不能因为前置解析把本来不改的部件标脏。
- 删掉的对象后面再点名时要能识别出来，报 `IdNotFound`。

候选做法：

- pptx：apply 开始时把 `slide:{n}` 换成该页的 `p:sldId/@id`，之后一律按 `sldId` 找页。这是文件里本来就有的稳定编号，不需要临时标记。
- docx：apply 开始时找到被点名的 `w:p`，给它挂一个本库专用的临时标记；之后按标记找，写回前统一摘掉。或者找到更简单、同样满足上面三条约束的做法。

还要核对 create 的内部调用：

- docx 和 pptx 的 create 都复用 apply 的 op。逐个核对它们是否在同一批里先插入、再按位置点名新对象。
- 有的话，改成分批调用，或者改用内容编号的 id，保证 create 的产物不变。

### 3–4. 实现

- 各格式 apply 入口在执行第一条 op 前做一遍前置解析。执行阶段只认解析结果。
- 解析失败（原文件里就没有这个对象）照旧报 `IdNotFound`，报错时机提前到执行第一条 op 之前。

### 5. 验收

- docx：缺陷记录的复现步骤做成测试，断言 P4 被改、P3 不变。
- docx：先删 `para:index:2`，再点名它，报 `IdNotFound`，不写文件。
- pptx：先删 `slide:1`，再改 `slide:3` 上的形状，改到的是原来的第 3 页。
- pptx：`moveSlide` 之后再点名被移动的页，指向的仍是同一页。
- 现有 docx、pptx 测试全过。依赖「按新顺序计」的测试改了期望：
  - `pptx_slides::later_op_uses_new_index` 改名为 `later_op_keeps_original_slide`。插入之后再改字，id 从 `slide:3/shape:2` 改成 `slide:2/shape:2`，改到的仍是原来的第二页。

- 手测：用 Word 16.0 和 PowerPoint 16.0 分别打开上面 docx 与 pptx 两条测试的产物，内容与断言一致。

## 审计发现的遗漏（2026-10-30）

固定的做法本身是对的：docx 用 `ooxp:pin` 标段落，pptx 用 `SlideFreeze` 冻结页名单。问题是只有一部分 op 接上了，其余 op 仍按当前顺序找对象。页数或段数多时，它们会静默改到别的对象上。契约（`docs/json-contract.md`「稳定 id」）已经承诺全部 op 都按 apply 开始时解释。

实测（先删或先插，再点名原来的对象）：

- docx：在 P1 后插一段，再对 `para:index:4`（原来的 P4）发下面的 op。
  - 对的：`setParaText`、`insertHyperlink`、`setParaFormat`、`insertFootnote`
  - 落到 P3 上的：`insertBookmark`、`insertPara`、`insertSection`
  - `deletePara` 删掉的是 P3，P4 还在
- pptx：4 页，删掉 `slide:1`，再对 `slide:3`（原来的 S3）发 op。
  - 对的：`setShapeText`、`setTransition`、`setSlideHidden`、`setNotesText`、`moveSlide`、`insertSlide`、`setSlideLayout`、`insertComment`、`insertShape`、`setShapePos`、`deleteShape`、`setShapeFormat`
  - `insertTable` 落到原来的 S4 上
  - `insertHyperlink` 写进了删页后排在第 2 位的那一页，不是原来的 S2
  - `insertField`、`insertConnector`、`insertMath` 也按当前顺序找页

代码上的原因：

- docx：`para.rs` 第 1416、1690、2351、2604 行与 `smartart.rs` 第 1232 行仍用 `idx == *n` 比当前位置，没有走 `index_matches`。还要查有没有别的模块自己数段落。
- pptx：只有 `apply.rs` 入口里直接取页的 10 处和 `slides.rs` 改用了 `frozen.get`。各对象模块里自己找页的地方没有接上。

补做时：

- 先把所有接受段落 id 或页 id 的 op 列成表，每种 op 一条「先增删、再点名原对象」的回归测试。表从 `help` 的 op 名单生成，避免再漏。
- 找段落、找页只留一个入口，各模块不再自己数位置。
