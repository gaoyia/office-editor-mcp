## 目标

用 Rust 做一套 **库加命令行工具**：入参是 JSON，能对 `.docx`、`.xlsx`、`.pptx` 做两件事，一是**新建文件**，二是**改文件里的局部内容**。不复刻 Word 的排版引擎，不实现 Excel 的计算引擎，不做 PowerPoint 完整的动画时间轴。

### 终极目标：全量

「全量」指对 `.docx`、`.xlsx`、`.pptx` 三种格式都做到全功能的增、删、改、查。**这是这个项目最终想到达的地方，不是本次计划的目标。** 本次计划一项都不按「全量」验收，写在这里只是为了让后续的设计选择往这个方向靠，别做出堵死路的决定。

### 本次计划的目标

本次说的「做完」，指的是这三条同时成立：新建和修改走的是同一套 JSON 契约；产出的文件 Office 能正常打开；只改文字的时候，常见样式能尽量保住。功能上只覆盖下面「要做的部分」那张表里列出的条目。

#### 1 文档先行 ⚠️

xlsx 的规格已落到 `docs/`。docx / pptx 只定了模块边界和 id 规则，契约正文未写。

1.1 写 `docs/`：模块划分（opc、xlsx、docx、pptx、json、cli）、inspect 树与 apply 补丁的数据流、错误类型。⚠️ 见 `docs/architecture.md`、`docs/errors.md`、`docs/opc.md`  
1.2 写领域 JSON 契约，`schemaVersion: 1`，`action` 取值为 `inspect`、`create`、`apply`。⚠️ 见 `docs/json-contract.md`（xlsx 写全）  
1.3 规定 inspect 树里稳定 id 怎么生成：xlsx 用工作表名加 A1 式地址；docx 用段落 id；pptx 用 slide 加 shape。⚠️ 见 `docs/json-contract.md`「稳定 id」  
1.4 规定 apply 不接受整棵树，只有 create 才允许从 JSON 生成新包。⚠️ 见 `docs/json-contract.md`「apply」  
1.5 等用户确认 1.1 到 1.4，再开工第 2 项及以后。❌  

#### 2 OPC 公共层 ❌

2.1 把 `.docx`、`.xlsx`、`.pptx` 当 ZIP 打开，列出里面所有部件的路径。❌  
2.2 读写 `[Content_Types].xml`、根级 `_rels/.rels` 和部件级的 `.rels`。❌  
2.3 按路径读出部件的字节；改完之后写回指定部件。❌  
2.4 保存时，没有改过的部件保持原来的字节，不重排顺序，也不去美化无关的 XML。❌  
2.5 验收：打开样例文件再原样保存，Excel、Word、PowerPoint 都能正常打开。❌  

#### 3.1 xlsx 读取与局部修改 ❌

3.1.1 `inspect`：列出工作表；按给定区域（例如 `A1:D20`）返回地址、显示值和公式字符串。默认不返回整本工作簿。❌  
3.1.2 `apply`：用 `setCell` 写入数字、文本、布尔值或者空值。❌  
3.1.3 `apply`：用 `setCell` 写入公式字符串（例如 `=SUM(A1:A10)`），库里不求值。❌  
3.1.4 改了公式或者它依赖的单元格之后，清掉过期的缓存值，或者标记成「打开时需要重算」。❌  
3.1.5 只改目标单元格所在的 XML，其他工作表和样式部件原样保留。❌  
3.1.6 验收：改掉若干个单元格之后 Office 能打开，没改的区域看上去和原来基本一样。❌  

#### 3.2 xlsx 新建 ❌

3.2.1 从 JSON 生成一个至少含一张工作表的空白或简易工作簿。❌  
3.2.2 JSON 里可以声明单元格的值和公式文本。❌  
3.2.3 产出的文件 Excel 和 WPS 都能打开。❌  

#### 4.1 docx 读取与局部修改 ❌

4.1.1 `inspect`：返回大纲（也就是各级标题）和段落列表，每段带稳定 id 和可见文本，可以按范围截断。❌  
4.1.2 `apply`：按段落 id 替换文本，尽量保留这一段现有的 run 和样式，不整篇重建 `document.xml`。❌  
4.1.3 本项不做修订痕迹、页眉页脚的精细编辑、复杂表格的结构编辑，这些见「暂缓」。❌  
4.1.4 验收：改掉一个段落之后，标题样式和其他段落都还在；Word 能正常打开。❌  

#### 4.2 docx 新建 ❌

4.2.1 从 JSON 生成简易文档，支持正文段落和标题样式。❌  
4.2.2 产出的文件 Word 能打开。❌  

#### 5.1 pptx 读取与局部修改 ❌

5.1.1 `inspect`：按页列出形状 id 和文本框里的可见文字。❌  
5.1.2 `apply`：按 slide 加 shape 改文字；不删掉形状再重建，因为形状 id 一变，绑在它上面的动画就会失效。❌  
5.1.3 不改 `<p:timing>`；完整写入动画见「暂缓」。❌  
5.1.4 验收：改掉一页的文字之后，其余页不变；PowerPoint 能正常打开。❌  

#### 5.2 pptx 新建 ❌

5.2.1 从 JSON 生成简易演示文稿，支持若干页和文本框。❌  
5.2.2 产出的文件 PowerPoint 能打开。❌  

#### 6 命令行 ❌

6.1 从文件路径或者 stdin 读入领域 JSON。❌  
6.2 按 `action` 的取值分发到 inspect、create、apply。❌  
6.3 inspect 把 JSON 树打到 stdout；create 和 apply 写出目标文件。❌  
6.4 本表不含 MCP。MCP 用的是同一套领域 JSON，另外开任务做传输层封装（当前倾向 JSON-RPC 2.0）。❌  

**建议顺序：** 1 → 2 → 3.1 → 3.2 → 6（先把 xlsx 这条路跑通）→ 4.1 → 4.2 → 5.1 → 5.2。

### 暂缓 💤

- PowerPoint 的通用动画时间轴：读出来列个清单可以放到二期，完整写入不做
- Word 的修订痕迹、页眉页脚精细编辑、复杂表格的结构编辑
- Excel 的公式求值、数据透视、图表渲染
- `.doc`、`.xls`、`.ppt` 这三种老的二进制格式
- 分页计算，以及与 Word 做到像素级一致

## 架构要点

- 自己实现 OPC 层，改内容时只动目标 XML 节点。不要把三套互不兼容的高层 crate 拼在一起当作唯一的文档模型。
- **不依赖** `office_oxide`。需要对照它的做法时，查它的公开仓库即可；不要在本仓库添加三方包目录或者 git 子模块，也不要写进 Cargo 依赖。
- 修改策略是**手术刀**：只改目标节点，不认识的命名空间和没碰到的部件都原样保留。这里对齐的是 Transitional 版 OOXML，也就是 Office 默认存出来的那种文件，与本项目「不考虑旧版兼容」的原则不冲突。
- **两层 JSON，不要混成一层：**
  - 领域契约：`inspect`、`create`、`apply` 这套文档操作 JSON，是库和命令行的入参。
  - 传输层：MCP 那一层的协议信封，当前倾向 JSON-RPC 2.0（走 stdio），领域 JSON 放进 RPC 的 `params` 里。不要拿 JSON-RPC 的信封结构去当单元格或段落的数据模型。
- **已经确认的交互方式：** 模型先读 `inspect` 返回的精简 JSON 树（树上带稳定 id），再发一份 `apply` 操作列表去改文件。在模型看来是「看着树改文档」，但真源始终是 OPC 里的 XML。禁止把 inspect 树当成完整的中间表示，改完之后整包重新生成；只有 `create` 新建文件时例外。
- 禁止把「先导出整份文档 JSON，再重新生成文件」当成修改路径。
- 查规范用 `standards/md/`，不要整本打开 ECMA-376 那份五千页的 PDF。

## 阶段出口

1. 空白的 xlsx、docx、pptx 都能从 JSON 新建出来，Office 能打开。
2. 对样例文件执行 apply，改一个单元格、一个段落或者一页文字之后，Office 能打开，没改的区域看上去和原来基本一样。
3. 公式只当字符串写进去，库里不求值。
4. 单元测试覆盖 JSON 契约和 XML 不变量，另外有一份人工打开文件的检查清单。
