# 错误信息多语言（中等难度）

状态：✅ 已落地
日期：2026-09-26

目标是让 `error.message` 能按语言渲染，默认英文。`code`、`path` 与命令行退出码全部不动，它们是给程序认的稳定契约。

2026-09-26 用户把七个设计点全部拍定，并要求按方案实现。pptx 当时已经用旧构造器写完，阶段 C 把 `pptx/` 一并迁了。没有引入 `#[deprecated]` 过渡构造器，调用点一次迁完。

## 现状盘点

错误现在是一个枚举，人话文案在**构造那一刻**就用 `format!` 烧成了 `String`：

```rust
pub enum Error {
    App { code: ErrorCode, message: String, path: Option<String> },
    Io(#[from] io::Error),
}
```

烧死之后无法事后翻译，这是要解决的根本问题。相关数字如下，都是从当前代码数出来的：

| 项 | 数 | 说明 |
| --- | --- | --- |
| 错误构造点 | 140 | `Error::new`、`Error::with_path`、`io_path` 三者合计 |
| 涉及文件 | 16 | 全在 `crates/ooxp/src/` 下 |
| 不同文案 | 约 100 | 按文本去重，跨文件重复的只算一条 |
| 断言文案的测试 | 0 | 现有测试只断言 `err.code()`，不看 `message` |
| `ErrorCode` 取值 | 17 | 本次一个都不改 |

测试一条都没有断言文案，这一点决定了迁移风险不大：改写 140 处构造点时，测试仍能守住「错误码有没有变」这条底线。

现有中文文案照搬为 `zh-CN` 的译文，只统一标点，不重写措辞。这些句子是写代码时逐处斟酌出来的，重写一遍只会引入新的偏差。英文是新写的那一份。

### 一条已经验证的限制

`Io` 变体的文案尾部来自操作系统，本身就带语言。在本机中文 Windows 上实测：

```text
{"error":{"code":"Io","message":"无法访问 C:\\nope\\missing.xlsx：系统找不到指定的路径。 (os error 3)"},"ok":false}
```

`系统找不到指定的路径。` 是 `io::Error` 的 `Display`，由系统按当前语言给出，我们控制不了。也就是说，只要把 `io::Error` 直接嵌进 `message`，「默认英文」这条就守不住。设计必须绕开它，见下文第五节。

## 不做的事

- 不改 `ErrorCode` 的取值、语义和退出码映射。
- 不翻译 inspect 树里的内容，那是文档里的原文。
- 不翻译命令行的 `--help`。clap 的帮助文本另算，本期不碰。
- 不引入第三方 i18n 框架（`fluent`、`rust-i18n` 等）。文案总量约 100 条，静态表加穷尽 match 就够，引框架反而多一层运行时查找和一份资源文件格式要维护。

## 设计

### 一、把「错误的身份」和「渲染成人话」分开

`Error` 只携带身份与参数，不携带语言；渲染推迟到最外层。这是整套方案的地基。

```rust
pub enum ErrorKind {
    SheetNotFound { name: String },
    ParaNotFound { id: String },
    MissingField { field: String },
    WrongType { field: String, expected: TypeName },
    OutOfRange { field: String, min: i64, max: i64 },
    MutuallyExclusive { a: &'static str, b: &'static str },
    SharedFormulaMaster { cell: String },
    // ……
}
```

`code()` 从 kind 推导，不再由调用方手填。这顺带修掉一类隐患：现在同一种错误在不同文件里可能填不同的 `code`，靠人记。

### 二、参数化归纳，把约 100 条文案压到 35 到 45 个 kind

现有文案里有大量同构的句子，值得归纳成带参数的 kind：

| 现有文案样式 | 出现处数 | 归纳成 |
| --- | --- | --- |
| `不认识的字段：{k}` | 5 | `UnknownField { field }` |
| `缺少 sheets`、`缺少 path`、`缺少 ref`、`缺少 op`、`缺少 id` 等 | 12 | `MissingField { field }` |
| `workbook 必须是对象`、`sheets 必须是数组`、`from 必须是整数` 等 | 21 | `WrongType { field, expected }` |
| `maxCells 允许范围是 1 到 20000`、`maxParas 允许范围是 1 到 5000` | 2 | `OutOfRange { field, min, max }` |
| `value 和 formula 不能同时出现` | 3 | `MutuallyExclusive { a, b }` |

语义性的错误不要硬塞进通用 kind。`至少需要一张工作表`、`工作表不能叫 History`、`共享公式的主格改不了` 这类各自留一个 kind，措辞才说得清。归纳的边界就是这一条：句子结构一样、只有名词变的，合并；讲的是具体业务规则的，独立。

### 三、每种语言一个文件，靠编译器保证不漏译

```text
crates/ooxp/src/error/
  mod.rs            Error、ErrorKind、ErrorCode、Lang
  messages/
    en.rs           pub fn render(kind: &ErrorKind) -> String
    zh_cn.rs        同上
```

每个 `render` 都是对 `ErrorKind` 的穷尽 `match`。新增一个 kind，两个文件都必须补分支，否则编译不过。新增一门语言就是加一个文件，再往 `Lang` 的 match 里挂一行。这比查表方案强的地方就在于漏译是编译错误，不是上线之后才发现的空字符串。

### 四、语言从哪来，什么时候定

先看一个绕不开的顺序问题：`InvalidJson` 这类错误发生在请求还没解析出来的时候，那时根本读不到请求里的语言字段。所以语言不能由库在出错时决定，只能由最外层在**渲染时**决定。

优先级定为：

| 来源 | 形式 | 说明 |
| --- | --- | --- |
| 请求 | `locale` 字段 | 最高。属于领域层，MCP 只能走这条路 |
| 命令行 | `--lang zh-CN` | 请求里没写时用 |
| 环境变量 | `OOXP_LANG` | 命令行没给时用 |
| 默认 | `en` | 都没有时用 |

请求优先于命令行参数，与 `docs/cli.md` 里 `--output` 的既有规则一致：命令行只在请求没给的时候补位。

第一期只做两门语言：`en` 与 `zh-CN`。

语言标签宽松匹配，不认识就退回英文，**不报错**。语言是呈现偏好，为了一个不认识的标签把整个文档操作拒掉，代价不成比例。匹配规则是先按连字符切开取首段，再看后面的地区或字形段：

| 输入 | 归到 |
| --- | --- |
| `zh`、`zh-CN`、`zh-Hans`、`zh-SG` | `zh-CN` |
| `en`、`en-US`、`en-GB` | `en` |
| `ja`、`de`、空串、乱码 | `en`（默认） |

这条是唯一一处对未知输入不报错的地方，与信封里 `deny_unknown` 的严格风格不同，要在 `docs/json-contract.md` 里写明理由，免得后来的人当成漏写的校验去补。

库导出 `pub fn peek_lang(input_json: &str) -> Option<Lang>`，只做一次浅解析，专门取 `locale`，解析不了就返回 `None`。命令行不必自己写这段 JSON 预解析。

`run()` 的签名不变，仍返回语言中立的 `Error`。`Error::to_json()` 改成 `to_json(lang: Lang)`。项目没有历史用户，按工程原则不考虑兼容，直接改签名。

公开接口只加 `Lang`、`peek_lang` 和改签名的 `to_json`。`ErrorKind` **不导出**，留在库内部。导出它等于承诺几十个 variant 的形状都稳定，而它正是本期要反复调整的东西；MCP 层拿 `code()` 加 `to_json(lang)` 已经够用。将来 MCP 真的需要自己分支，再单独评估导出。

`Display` 只能给一种语言，定为**恒用英文**。`thiserror` 的 `#[error("{message}")]` 要换成手写实现。这条影响 `unwrap()` 的 panic 输出和上层 `anyhow` 的打印，写进文档说清楚。

### 五、Io 错误怎么保住语言

不再把 `io::Error` 的 `Display` 嵌进 `message`，改成我们自己的模板加上系统错误码：

```text
en:     Cannot access "C:\nope\missing.xlsx" (os error 3)
zh-CN:  无法访问「C:\nope\missing.xlsx」（os error 3）
```

`os error 3` 由 `raw_os_error()` 取，可查、可搜、与语言无关。

系统给的那句原文放进新的可选字段 `osMessage`，信息不丢，也不污染 `message` 的语言。出错形状变成这样：

```json
{
  "ok": false,
  "error": {
    "code": "Io",
    "message": "Cannot access \"C:\\nope\\missing.xlsx\" (os error 3)",
    "osMessage": "系统找不到指定的路径。"
  }
}
```

`osMessage` 只在 `Io` 这一类错误上出现，且只在系统确实给了原文时才有。它的语言由操作系统决定，我们不承诺是哪一门，文档里要写清这一点，免得调用方拿它去做字符串匹配。这是本期唯一一处改动错误输出形状的地方，要同步改 `docs/errors.md`。

## 要改的文档

按「先改文档，等确认，再动代码」的规矩，这批文档要先改到位：

| 文档 | 改什么 |
| --- | --- |
| `docs/errors.md` | 把「`message` 是中文或英文短句」改成语言规则；补 `locale` 与 `--lang` 的优先级；补 `osMessage` 字段；说明 `Display` 恒用英文 |
| `docs/json-contract.md` | 信封表加可选字段 `locale`，写清取值与未知值的处理 |
| `docs/json-schema/request.schema.json` | 三处 `additionalProperties: false` 的 `properties` 都要加 `locale`，否则请求会被拒 |
| `docs/cli.md` | 调用式加 `--lang`；参数表加一行；补 `OOXP_LANG` |
| `docs/architecture.md` | 模块树里加 `error/messages/`；写明依赖方向是各模块只依赖 `error`，不反向依赖 |

代码那边对应要改 `dispatch.rs` 里三处 `deny_unknown` 的白名单，把 `locale` 放进去。漏掉这一步，带 `locale` 的请求会直接报 `InvalidField`。

## 与 pptx 并行

冲突集中在三个文件：`error.rs` 双方都要加东西，`dispatch.rs` 与 `json.rs` 里 pptx 要把 `NotImplemented` 换成真实分支。

已定的办法是阶段 B 先合并。它只动 `error.rs`，不碰任何调用点，改动面窄，可以先落地。合并之后 pptx 的新代码直接用新的 kind 接口，不要用 `#[deprecated]` 的旧构造器，这样 pptx 的错误文案一次就写对，不必等阶段 C 再改一遍。

为此阶段 B 多担一件事：`ErrorKind` 里 pptx 要用的 kind 也在阶段 B 一起定好并写完两种语言的文案，pptx 直接拿来用。按 `docs/json-contract.md` 已定稿的 pptx 契约，至少要覆盖找不到幻灯片、找不到形状、缺少 `scope.slide`、`presentation` 与 `workbook` / `document` 互斥这几类。定不全会逼着 pptx 那边临时用旧构造器，等于把阶段 D 的债又欠回来。

`dispatch.rs` 与 `json.rs` 仍排在阶段 C4，等 pptx 把 `NotImplemented` 那几处换掉之后再动，避免两边同时改同一批行。

### 实际是反着走的 ⚠️

上面这套顺序没有照办。pptx 第一期（`ce4e0e3`）先用旧构造器写完并合并，多语言机制（`c9ff0e6`）随后一次性把 `pptx/` 连同其余文件一起迁到新 kind。结果与计划要的一样：仓库里没有旧构造器残留，pptx 的文案两种语言都齐。之所以没出乱子，是因为两件事由同一个人先后做完，并没有真的并行。如果换成两条并行的分支，`error.rs`、`dispatch.rs`、`json.rs` 这三个文件就会撞车，这套顺序仍然是对的。

## 验收标准

- 每个 kind 在 `en` 与 `zh-CN` 下都渲染出非空文案，且不含未替换的占位符。用宏定义 kind 并同时生成样本表，新增 kind 自动进测试，避免手写样本表漏项。
- 语言来源的优先级有测试覆盖：请求 `locale` 压过 `--lang`，`--lang` 压过 `OOXP_LANG`，都没有时是英文。
- 宽松匹配有测试：`zh`、`zh-Hans`、`zh-SG` 都出中文；`ja`、空串、乱码都退回英文且不报错。
- 不带 `locale` 的请求，`message` 是英文；`Io` 错误的 `message` 里不出现系统语言的句子，系统原文只出现在 `osMessage` 里。
- `ErrorKind` 没有出现在库的公开接口里。
- 17 个 `ErrorCode` 与退出码的对应关系不变，现有测试全绿。
- 五份文档与代码一致，`request.schema.json` 能通过带 `locale` 的请求。

## 风险

- 140 处迁移里可能把 `code` 填错。测试只断言 code，能挡住已覆盖的路径，未覆盖的路径挡不住。缓解办法是 `code()` 由 kind 推导，同一种错误只在一处定 code。
- 英文文案要人过一遍。机器直译出来的英文短句容易读着别扭，尤其是归纳过的那几个通用 kind。
- `Display` 恒用英文，中文用户直接 `unwrap()` 时看到的是英文。这是 Rust `Display` 不带参数导致的，只能这样。
