# 请求拒绝非法 XML 字符

状态：❌ 未开始。
日期：2026-10-30

不在三种格式的待做表里，不占待做序号。这是缺陷修复，记录见 `.bugfix-reports/2026年-10月-30日-❌-非法XML字符原样写出.md`。

排在 2026-10-30 审计拆出的重构计划前面。

用户 2026-10-30 决定：三种格式统一报错，不按 `_xHHHH_` 转义，也不静默删掉。

## 目标

领域 JSON 里任何字符串（值或键）含有 XML 1.0 不允许的字符时，整个请求被拒绝，不写文件，错误指出是哪个字段、哪个码位。

不允许的字符：

- U+0000–U+0008
- U+000B、U+000C
- U+000E–U+001F
- U+FFFE、U+FFFF

TAB、LF、CR 允许。Rust 字符串里不会出现代理项，不用另查。

## 不做

- 不检查调用方传入的二进制文件（图片、音视频、OLE、墨迹、3D、字体）。
- 不检查已有包里的 XML。它们是解析出来的，本来就合法。
- 不按 xlsx 的 `_xHHHH_` 规则转义。

### 1. 文档

- `docs/json-contract.md` 的信封一节加一条：请求里所有字符串不得含有上面列出的字符，否则报错。
- `docs/errors.md` 登记新错误：
  - 错误码 `InvalidField`
  - `path` 指向字段，例如 `ops[2].text`、`workbook.sheets[0].cells[3].value`
  - 文案带码位，例如 `U+000B`
- 看一遍 `help` 的说明文字，要提的话一并补上。

### 2. 错误种类

- `error/kind.rs` 新增一种，带码位字段。错误码映射到 `InvalidField`。
- `messages/en.rs`、`messages/zh_cn.rs` 各补文案。

### 3. 检查位置

- 放在 `json::parse_request` 里，解析成功之后、交给 `dispatch` 之前。
- 递归走值和键，一边走一边记 JSON 路径，遇到第一个非法字符就报错。
- 这里是所有用户字符串唯一共同经过的地方：本机 `run`、`run_bytes`、`ooxp mcp` 的 `requestPath` 都经过它。元素树写出和 `format!` 拼接两条路都不用各自再查。

### 4. 回归测试

- 三种格式各一条：create 或 apply 的文本里带 U+0001 或 U+000B，返回 `InvalidField`，`path` 正确，目标文件没有生成或没有被改。
- 键里带非法字符同样报错。
- TAB、LF、CR、中文、emoji 照常通过。
- `cargo test -p ooxp --lib --tests` 与 `cargo test -p ooxp-cli` 全过。
- `cargo fmt --all` 与 `cargo clippy --all-targets --all-features -- -D warnings` 通过。
- 被拒绝的请求不写文件，不要求 Office。
