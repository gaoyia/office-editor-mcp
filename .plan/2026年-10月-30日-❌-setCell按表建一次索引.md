# setCell 按表建一次索引

状态：❌ 未开始。
日期：2026-10-30

不在三种格式的待做表里，不占待做序号。来源是 2026-10-30 第二轮代码审计。领域 JSON 不变，写出的 XML 不变。

## 现象

2026-10-30 用 release 构建实测：

| 场景 | 耗时 |
| --- | --- |
| create 一张 2 万格的表 | 60 ms |
| 在这张表上 apply 500 条 `setCell` | 0.62 s |
| 同上 1000 条 | 1.24 s |
| 同上 2000 条 | 2.51 s |

每条约 1.2 ms，和条数成正比，每格比 create 慢约 40 倍。按代码推断，每条的耗时还和表的大小成正比。

## 怀疑的热点

按工程原则，先定位再优化。下面只是读代码得到的怀疑，第 1 步要用剖析结果确认：

- `xlsx/apply.rs` 的 `apply_set_cell` 每条 op 都调 `formula::index_sheet`，把整张 `sheetData` 扫一遍，建共享公式、数组公式、数据表索引。
- `ensure_cell` 里 `find_row_insert_pos` 线性扫行，而且连扫两遍（`ensure_row` 一遍，回头再找一遍）；`find_cell_insert_pos` 同样扫两遍。
- `xlsx/inspect.rs` 读单元格时也建一次索引，那里每次 inspect 只建一次，不是问题。

## 不做

- 不改 `setCell` 的公式语义（共享公式、数组公式、数据表的拆分与保留规则）。
- 不为了性能改 `sheetData` 的 XML 形状。
- 不碰 create。它走字符串拼接，已经够快。

### 2. 公式索引

- 索引跟着脏表走：第一次碰这张表时建，之后复用。
- 只有改变公式布局的写入才让索引失效或增量更新：写公式、拆共享组、写数组公式、写数据表。
- 写纯值的格子不在任何公式组里时，不重建索引。
- 用剖析结果判断增量更新是否值得，不值得就失效重建。

### 3. 定位

- `<row>` 按 `r` 升序排列，可以二分查找；`<c>` 在行内按列升序，同理。
- 先确认文件里出现乱序或缺 `r` 时怎么退回线性扫描。缺 `r` 的情况见另一份计划「xlsx 隐式行列位置」，两份不要同时改这几个函数。
- `ensure_cell`、`ensure_row` 一次找到位置就用，不再回头找第二遍。

### 4. 验收

- `xlsx_formula`、`xlsx_fidelity` 等现有测试全过，不改期望值。
- 复测上表三个场景，2000 条 `setCell` 降到 0.3 s 以内。复测数字写回本计划。
- `cargo fmt --all` 与 `cargo clippy --all-targets --all-features -- -D warnings` 通过。
- 写出的 XML 与改动前逐字节相同，不要求 Office。
