# 非法 XML 字符原样写进文件

状态：❌ 未修复。修复切片见 `.plan/2026年-10月-30日-❌-请求拒绝非法XML字符.md`
日期：2026-10-30
影响面：三种格式所有接受用户文本的 op 与 create 字段

## 怎么发现的

2026-10-30 第二轮代码审计时，在全库搜索 XML 字符合法性检查，一处都没有。

XML 1.0 §2.2 只允许 TAB、LF、CR 和 U+0020 以上的字符，另外还排除 U+FFFE、U+FFFF。U+0000–U+0008、U+000B、U+000C、U+000E–U+001F 都不能出现在文档里，写成字符引用也不行。

## 现象

用临时测试实测：

- xlsx create 时单元格写 `"a\u0001b\u000Bc"`，`xl/sharedStrings.xml` 里出现原样的 0x01 和 0x0B。
- docx create 时段落写 `"x\u0001y"`，`word/document.xml` 里出现原样的 0x01。
- 库返回成功，用自己的 inspect 也读得回来。Office 打开会报内容有问题。

U+000B（垂直制表）在从 Word 复制出来的文本里很常见，模型转述用户文本时很容易带进来。

## 根因

请求里的字符串一路原样进入 XML：

- 走元素树的，由 `xml.rs` 写出，quick-xml 不检查字符合法性。
- 走 `format!` 拼字符串的，`escape_text` / `escape_attr` 只做实体转义。

quick-xml 读取时也不检查，所以库自己读得回来。

## 修法（计划）

按用户 2026-10-30 的决定：三种格式统一报错，不转义，也不静默删掉。

- 在领域 JSON 信封这一层统一检查：`parse_request` 解析完以后递归走一遍所有字符串值，遇到非法字符就报错。错误路径指向具体字段，例如 `ops[2].text`。
- 新增一个错误种类，错误码归 `InvalidField`，文案带上码位（如 `U+000B`）。
- 先改 `docs/json-contract.md` 信封一节与 `docs/errors.md`。

放在信封层，是因为这是所有用户字符串唯一共同经过的地方。元素树写出和 `format!` 拼接两条路都不用各自再查。

## 教训

和属性换行那份记录相同：用自己的宽松解析器读回来判卷，测不出 Office 会拒绝的东西。另外，「库从不检查某类输入」本身就值得在审计里单独搜一遍。这次就是一句 grep 搜出来的。

## 回归测试（计划）

- 三种格式各一条：请求里带 U+0001 或 U+000B，返回 `InvalidField`，错误路径指向该字段，不写文件。
- TAB、LF、CR 和 U+0020 以上的普通字符不受影响。
- 字段名（对象的键）里有非法字符同样报错。
