# 按位置编号的 id 在同一次 apply 里漂移

状态：✅ 第一期已修好。段落 id 与 `slide:{n}` 都按 apply 开始时解释。其余位置编号仍见计划文末的第二期。修复切片见 `.plan/2026年-10月-30日-✅-apply开始前固定id.md`。
日期：2026-10-30
影响面：docx 没有 `w14:paraId` 的文件（LibreOffice、Google Docs 等非 Word 来源常见）；pptx 一切带 `slide:{n}` 的批次。其余按位置编号的 id 同类。

## 怎么发现的

2026-10-30 第二轮代码审计。`docs/json-contract-docx.md` 写的是：`para:index:{n}`「在增删段落后会变，只够同一次 inspect 之后立刻 apply」。

但 `docs/json-contract.md` 规定 apply 的 `ops` 按数组顺序执行。同一次 apply 里，前面的 op 一旦增删段落，后面的 op 拿的还是 inspect 时的编号。

## 现象

用临时测试实测：

- create 一份 5 段的 docx（P1–P5），再把 `w14:paraId` 全部去掉，模拟非 Word 来源的文件。
- 一次 apply 发两条：先 `insertPara`（id 为 `para:index:1`），再 `setParaText`（id 为 `para:index:4`，按 inspect 结果就是 P4）。
- 结果是 P3 被改写，P4 原样，没有任何报错。

这是静默改错对象，文件完全合法。

pptx 的 `slide:{n}` 也是同一类：`insertSlide` / `deleteSlide` / `moveSlide` 之后，后面 op 里的页号指向别的页。pptx 契约第 228 行把这写成了规则，所以不算实现偏差。但调用方是模型：它从 inspect 拿 id，一次发出一批 op，基本不可能自己算对重新编号后的页号。

## 根因

各格式的 apply 每执行一条 op，都按当时的树重新解析该 op 的 id。位置编号的 id 因此跟着前面 op 的增删漂移。

三种格式按位置编号的 id 有很多：

- docx 与各格式的 `:index:{k}` 退路
- xlsx 的 `dv:{n}`、`cf:{n}`、`table:{n}`、`name:{n}` 等
- docx 的 `section:{n}`、`table:{n}/r{r}c{c}`、`bookmark:{n}` 等
- pptx 的 `slide:{n}`、`master:{n}`、`layout:{k}`

## 修法（计划）

按用户 2026-10-30 的决定：apply 开始前，把所有 op 里的 id 都按原文件解析成节点；后面的 op 不受前面增删的影响。

- 被前面 op 删掉的对象，后面再点名时报 `IdNotFound`，不落到别的对象上。
- pptx 契约第 228 行改成同一规则。
- 分两期：第一期 docx 段落类 id 与 pptx `slide:{n}`，已实测出问题；第二期按上面的清单铺到其余位置 id。

## 教训

测试样本几乎都来自本库的 create，而 create 一定会写 `w14:paraId`。所以 `para:index` 只在「先 inspect 再 apply 一条」的场景里测过，从来没有在「一批里先增删再引用」的场景里测过。

这又是同一条教训：拿自己的输出当测试输入。

另一条：契约里「只够同一次 inspect 之后立刻 apply」这种说法，没有回答「立刻 apply 的那一批里有增删怎么办」。写 id 规则时，必须写明它在一批 op 内部的语义。

## 回归测试

- docx：本记录的复现步骤原样做成测试，断言 P4 被改、P3 不变。
- docx：先 `deletePara` 删掉 `para:index:2`，再点名它，报 `IdNotFound`。
- pptx：先删 `slide:1`，再改 `slide:3` 上的形状，改到的是原来的第 3 页。

## 第一轮修复之后又摔了一次（2026-10-30 审计）

上面三条回归测试都过了，计划也标了 ✅，但审计换了几种 op 再测，docx 的 `deletePara`、`insertPara`、`insertBookmark`、`insertSection` 和 pptx 的 `insertTable`、`insertHyperlink`、`insertField`、`insertConnector`、`insertMath` 仍按当前顺序找对象。其中 `deletePara` 静默删掉了旁边那一段。

原因是回归测试只覆盖了写缺陷记录时用的那一两种 op。固定 id 的机制是对的，但找段落、找页的代码散在各对象模块里，只有被测试点到的那几处接上了。

教训：修「所有 op 的 id 语义」这类横向缺陷，回归测试必须按 op 名单逐个覆盖，名单要从 `help` 的 op 列表生成，不能只用复现时的那一两条。

第二次补做后又查出 5 处（2026-10-30 第二次审计）：pptx 的 `insertSlide` 节归属、`insertZoom` 目标页、自定义放映页名单、`setSlideSection`、`insertSlideSection` 的 `start`。原因相同：节和自定义放映直接读 `sldIdLst` 的当前顺序，没有经过冻结名单；第二次补做也只按上次报出的那几种 op 加了测试，仍没有按 op 名单逐个覆盖。这 5 处已修，回归测试见 `pptx_slides.rs`。
