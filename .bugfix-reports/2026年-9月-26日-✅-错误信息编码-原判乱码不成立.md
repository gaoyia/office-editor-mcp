# 错误信息编码：原判「Windows 控制台会把中文显示成乱码」不成立

状态：✅ 复核判定不是缺陷，不改代码，只补文档  
日期：2026-09-26  
影响面：命令行的 stdout 与 stderr。错误文案默认英文，非 ASCII 只出现在两处——请求选了中文，以及 `Io` 错误的 `osMessage`（装的是系统给的原文）

这一份记的不是缺陷，是一条挂了一天的审计项被判定为误判的过程。留下来的价值在方法：**查编码问题时，用来观测的工具本身就在编码链上，稍不留神就会得出一个自洽但错误的结论。** 我在复核中途正是这样错了一轮。

## 原判是什么

审计表 A8 原文：

> Windows 控制台默认代码页不是 UTF-8，错误信息里的中文在终端里会显示成乱码。字节本身是 UTF-8，符合 `docs/cli.md`，但用户看到的是乱码。

这条写得有依据的样子——本机 `chcp` 确实是 936，而 Rust 的 `String` 确实是 UTF-8，两者一对就「显然」会乱。加上我在终端里真的看到过乱码，就顺手记成了缺陷。

用户提的要求是别写死 UTF-8，问能不能查出系统当前跑在什么编码下，按优雅的方式处理，不留技术债。于是先查清事实，再谈方案。

## 复核第一轮：得出了一个错误结论

第一个实验是拿 PowerShell 起子进程，抓 stderr 的原始字节，分别用 UTF-8 和 CP936 解码，再把两种结果打印出来对比。输出是这样：

```text
as UTF-8 : {"ok":false,"error":{"code":"Io","message":"�޷����ʡ�C:\\nope\\missing.xlsx����os error 3��", …
as CP936 : {"ok":false,"error":{"code":"Io","message":"无法访问「C:\\nope\\missing.xlsx」（os error 3�?, …
strict UTF-8 decode: OK (bytes are valid UTF-8)
```

按字面读，CP936 才解得出中文，UTF-8 解出来是乱码，也就是 ooxp 写出的是 GBK 字节。这个结论和第三行自相矛盾：严格 UTF-8 解码明明说这些字节合法。而且它和 Rust 的类型系统冲突——`String` 是 UTF-8，`eprintln!` 不会凭空转码。

**矛盾的根源是我漏算了一层。** 打印这两行时，PowerShell 要把解码得到的 .NET 字符串重新编码成字节写给管道，我的工具再按自己的假设解码。链条实际上是三层，不是一层：

```text
ooxp 写字节 → PowerShell 解码成字符串 → PowerShell 重新编码 → 我的工具解码 → 我看到的字
```

我以为在观测第一层，其实看到的是三层叠加的结果。中间两层的编码假设不一致时，「哪种解法出中文」这个信号完全不可信。

## 复核第二轮：只看十六进制

关键是找一个不受编码链影响的观测方式。十六进制是纯 ASCII，怎么转码都不变形，于是把字节 dump 成 hex，同时打印两种编码下「无法访问」这四个字的参考值。在 936 代码页下的结果：

```text
chcp             : 936
Console.OutputEnc: 936
GetACP           : 936

raw length : 152 bytes
… 22 6d 65 73 73 61 67 65 22 3a 22 e6 97 a0 e6 b3 95 e8 ae bf e9 97 ae e3 80 8c …
                  ^ "message":"    ^ 无            法          访          问

UTF-8  bytes of 无法访问: e6 97 a0 e6 b3 95 e8 ae bf e9 97 ae
CP936  bytes of 无法访问: ce de b7 a8 b7 c3 ce ca
```

`"message":"` 之后是 `e6 97 a0 e6 b3 95 e8 ae bf e9 97 ae`，与 UTF-8 参考值逐字节相同；GBK 会是 `ce de b7 a8` 那一串。**在代码页 936 的会话里，ooxp 写出的就是 UTF-8。** 又把同一批字节落盘，用另一条独立通道（按 UTF-8 读文件的编辑器）读出来，中文完整正确，与 hex 结论一致。

回头能把第一轮那个假象解释干净了。真相是 PowerShell 按 936 编码写管道，而我的读取端按 UTF-8 解码，两层假设不一致。于是「用错的解码方式」那一行反而显示正确：

```text
CP936 那一行： UTF-8 字节 --按 GBK 解--> 乱码字符串 --按 GBK 编码--> 又变回原来的 UTF-8 字节 --读取端按 UTF-8 解--> 正确中文
UTF-8 那一行： UTF-8 字节 --按 UTF-8 解--> 正确字符串 --按 GBK 编码--> GBK 字节 --读取端按 UTF-8 解--> 一片 U+FFFD
```

GBK 的解码与编码在这批字节上是可逆往返，把原始 UTF-8 原封不动地还原了出来，正好迎合读取端的假设；而真正解对的那一行，反倒在后面两层被拆坏。末尾几个字符仍有破损，是 GBK 解码撞上落单字节所致。三条信息至此全部自洽：字节是 UTF-8，严格解码通过，两行显示的反常只是观测链的产物。

## 控制台那一格：Rust 标准库已经绕过了代码页

字节是 UTF-8 说明了管道情形，还剩「输出直接接控制台」这一格。原判的要害正在这里：代码页 936 的控制台收到 UTF-8 字节，不该显示成乱码吗？

答案是标准库根本没让它按代码页解释。`library/std/src/sys/stdio/windows.rs`（rustc 1.96.0）里 `Stdout::write` 与 `Stderr::write` 走同一个函数，下面是节选，省去了直写分支里的 `unsafe` 细节：

```rust
fn write(handle_id: u32, data: &[u8], incomplete_utf8: &mut IncompleteUtf8) -> io::Result<usize> {
    let handle = get_handle(handle_id)?;
    if !is_console(handle) || is_utf8_console() {
        // 直接把字节写下去
    } else {
        write_console_utf16(data, incomplete_utf8, handle)
    }
}

fn is_console(handle: c::HANDLE) -> bool {
    // GetConsoleMode 对管道返回 false，正好只挑出 Windows 控制台
    let mut mode = 0;
    unsafe { c::GetConsoleMode(handle, &mut mode) != 0 }
}

fn is_utf8_console() -> bool {
    unsafe { c::GetConsoleOutputCP() == c::CP_UTF8 }
}
```

`write_console_utf16` 用 `MultiByteToWideChar(CP_UTF8, …)` 把 UTF-8 转成 UTF-16，再交给 `WriteConsoleW`。宽字符 API 不经过代码页，因此代码页是多少都不影响显示。另外 `is_utf8_console` 在 Windows 7 上是另一份实现，恒返回 false，也就是永远走 `WriteConsoleW`，结论不变。三种情形合起来：

| 情形 | 实际写出的东西 | 结果 |
| --- | --- | --- |
| 输出接管道或文件 | UTF-8 字节 | 正确，符合 `docs/cli.md` |
| 输出接控制台，代码页不是 65001 | 转成 UTF-16 走 `WriteConsoleW` | 正确，与代码页无关 |
| 输出接控制台，代码页是 65001 | UTF-8 字节 | 正确，控制台按 UTF-8 解释 |

三格都是对的，所以 A8 描述的现象不存在。**我当初确实看到过乱码，但那发生在管道情形，而且是读的一方按 936 去解 UTF-8 字节** ——责任在读方的配置，不在 ooxp。同一段字节，把读方的解码方式定成 UTF-8 就完全正常，这一点在复核里反复验证过。

## 那些看起来更优雅的方案，为什么都不做

用户问的「能不能知道当前系统跑在什么编码下」，答案是能：`GetConsoleOutputCP` 拿控制台输出代码页，`GetACP` 拿 ANSI 代码页，PowerShell 里读 `[Console]::OutputEncoding.CodePage` 也行。但知道之后的三条路都比现状差。

**一、启动时调 `SetConsoleOutputCP(65001)` 把控制台切到 UTF-8。** 一行代码就能让「字节直写」这条路在控制台下也正确，但它改的是调用方控制台的全局状态，进程退出后不会自动复原，后面的命令跟着受影响。要复原就得在退出时改回去，而 panic 或者被 kill 时那段代码根本不会执行。为了一个本来就不存在的问题去动全局状态，是负收益。

**二、检测到控制台后，把 UTF-8 按当前代码页转码再输出。** 要引入编码转换依赖，而且 GBK 装不下所有字符——日文假名、少见汉字、emoji 都会丢成问号。丢的还偏偏是错误信息本身，正是用户最需要看清的东西。标准库那条 `WriteConsoleW` 的路子严格更优：它绕开代码页，不存在「目标编码装不下」的问题。

**三、写死 UTF-8。** 用户说过评估下来要写死也能接受。但现状已经是 UTF-8 了，而且是在「管道直写字节、控制台走宽字符 API」这个更精细的基础上的 UTF-8。写死反而是退化。

结论落在不改代码。技术债不在实现里，在那句写错了的审计描述和缺失的文档说明。

## 落到文档上的改动

`docs/cli.md` 的「编码与路径」原先只有一句「输入输出 JSON 均为 UTF-8」，现在补上了上面那张三情形表、不调 `SetConsoleOutputCP` 的理由，以及读方该怎么配。PowerShell 捕获输出前先把解码方式定下来：

```powershell
[Console]::OutputEncoding = [System.Text.UTF8Encoding]::new($false)
```

用 `ProcessStartInfo` 时改设 `StandardOutputEncoding` 与 `StandardErrorEncoding`。`manual-check/lib/common.ps1` 一直是这么写的，这也解释了为什么手测脚本从来没遇到过乱码，而我在临时命令里遇到了。

审计表 A8 的描述连带改掉了。原判的措辞会误导后来人去动 `SetConsoleOutputCP`，留着比删掉更危险。

## 附带发现：JSON 解析失败时读不到 locale

第一轮实验里我把请求写成 `"path":"C:\nope\missing.xlsx"`，反斜杠没在 JSON 里转义，于是先撞上 `InvalidJson`，而返回的 `message` 是英文的 `Input is not JSON: invalid escape at line 1 column 55`。

这不是 bug，正好验证了设计：`locale` 在请求体里，请求体解析失败就无从读取，此时只能退回 `--lang`、环境变量 `OOXP_LANG`，最后到默认英文。`peek_lang` 的降级行为符合 `.plan/2026年-9月-26日-✅-错误信息多语言.md` 的约定。

## 回归测试

编码这件事没法靠新增用例证明「没有缺陷」，能做的是把结论钉住，别让它悄悄退化。

`crates/ooxp-cli/tests/cli.rs` 的 `run_fail` 原先用 `String::from_utf8_lossy` 读 stderr。lossy 会把非法字节静默换成 U+FFFD，恰好能掩盖「stderr 不是 UTF-8」这种退化。现在改成严格解码：

```rust
// 严格解码，不用 lossy：stderr 必须是 UTF-8，管道场景不受控制台代码页影响。
let stderr = String::from_utf8(out.stderr).expect("stderr 不是 UTF-8");
```

走 `run_fail` 的 5 个语言用例于是一起成了这条结论的守卫。其中 `locale_beats_lang_flag`、`lang_flag_beats_env`、`env_lang_used_when_no_locale_or_flag` 三个断言的是中文文案 `schemaVersion 必须是 1`，`error_default_is_english` 与 `unknown_locale_falls_back_to_english` 断言英文。只要 stderr 的字节不再是合法 UTF-8，严格解码这一步就先炸；即便勉强解出来，那三条中文断言也对不上。

## 教训

**查编码问题时，观测工具本身就在编码链上。** 这是本次最值得记的一条。「用 A 解码出了正确结果」这类信号在多层转码下毫无意义，因为中间任何一层的编码假设不一致都会让结论翻转，而且翻转后的结果往往看起来非常自洽。可靠的办法是找一个不随编码变形的表示——十六进制、码位、字节长度，或者把字节落盘再用一条独立通道读。

**别把两个各自正确的事实直接相乘。** 「本机代码页是 936」是真的，「Rust 的字符串是 UTF-8」也是真的，但推不出「控制台会乱码」，因为中间还有标准库这一层。原判就是这么来的：两个正确的前提，加一个想当然的连接，得出一个错误的结论，还带着「显然如此」的自信。缺陷记录里凡是出现「因此显然」，都该回头补一次实测。

**先问「这个缺陷复现了吗」，再问「该怎么修」。** A8 挂着的这一天里，讨论的一直是修法——是不是该调代码页、该不该写死 UTF-8——却没人回头验证现象本身。差一点就为了一个不存在的问题引入一处会污染全局状态的改动。

**读一遍标准库比猜十遍强。** `is_console` 加 `is_utf8_console` 这两个判断，把三种情形都盖住了，这件事在 std 源码里是明写的，本地 rust-src 组件就有，查证只花了几分钟。平台相关的行为，标准库通常已经处理过，动手包一层之前先确认它没做。

## 还没解决的

**控制台那一格没有人眼确认过。** 结论由两条证据推出：std 源码里那条 `WriteConsoleW` 的路径，以及管道情形下的字节实测。但「在 936 代码页的 conhost 里，人眼看到的是正确中文」这一步始终没人验证过——我的观测环境只有管道，`is_console` 在那里返回 false，走的根本不是控制台分支。要补的话得在真控制台里跑一次并肉眼确认，或者读控制台屏幕缓冲区。

**结论依赖标准库的实现，不是 ooxp 自己保证的。** 控制台那一格的正确性来自 Rust std 的 Windows 后端。这是稳定行为，但一旦将来那段实现变了，这一格会跟着变，而 ooxp 这边不会有任何测试报警——现有测试只覆盖管道情形。

**路径里的非法 Unicode 序列没查。** Windows 的文件名是 UTF-16，理论上可以含不成对的代理项。这种路径进到错误消息里，`Path::display()` 会用 U+FFFD 替换，于是消息里的路径和真实路径不完全一致。这条既没构造样本也没验证过，只是记下来，与本次编码结论无关。
