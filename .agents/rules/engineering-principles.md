# 工程原则

本项目是从零开始写的新东西，没有历史用户，所有改动都不用考虑向旧版本兼容。

## 核心信条

1. **先想清楚架构，再写代码**：大改动之前，先把边界划出来，把每个模块负责什么、谁依赖谁说明白。凡是涉及跨模块的行为、性能问题或者系统边界的问题，都要先有顶层设计和数据流的判断，然后才动手实现。
2. **不留技术债**：不允许用临时的绕路办法盖住真正的架构问题。如果确实要先做一个短期修复，必须把它的边界写清楚，并且把通向正确方案的计划补上。禁止「先凑合，以后再说」。临时方案要注明什么时候还、怎么还，写不出来就不许合并。
3. **一个阶段一个阶段地推进**：每个阶段都要交出能验证的成果，并且事先写明入口条件、出口条件和验收标准。改动要守住现有的模块边界。凡是动到架构的改动，都要配上三样东西：覆盖核心不变量的单元测试、记录运行时假设的文档、用来人工验收的检查清单。
4. **文档先行，同步演进**：规格和契约以 `docs/` 为真源，也就是唯一可信来源。要新增或者改变行为时，**先改文档，再写代码**；代码合并的时候，文档必须在同一批里改到位。没有文档依据的实现不许写，只改代码、把文档欠着也不许。
5. **先计划，后实施，再验证**：这三步是一个闭环，一步都不能跳。
6. **说话要让人听懂**：与用户沟通时的措辞、结构和排版，一律按 `.agents/rules/output-style.md` 执行。

## 工作流

| 阶段 | 要求 |
|------|------|
| 计划 | 写明目标、范围、对架构的影响、阶段怎么分、验收标准是什么；如果动到契约、页面或 API，先把要改的文档列出来 |
| 文档 | 更新对应的 `docs/`，并确认新写的内容与已经定下的约束没有冲突 |
| 实施 | 按更新后的文档实现，改动控制在必要范围内，不引入没有记录的债务 |
| 验证 | 跑测试，核对文档与实现是否一致，确认这个阶段的出口条件都已满足 |

任务复杂就先把计划输出来（可以切到 Plan 模式），等用户确认，或者范围本身已经足够清楚，再开始实施。动手之前先确认相关文档已经更新，或者已经说明清楚「本阶段只改文档」。

## 缺陷处理

遇到 Bug，**不许**在 Agent 模式下凭猜测直接改代码。要提醒用户切到 **Debug 模式**，拿运行时的证据（日志、堆栈、复现步骤）定位到根因，然后才修。

遇到性能问题，先找到到底卡在哪里：是阻塞点、同步边界、数据拷贝，还是事件调度出了问题；定位清楚之后再决定优化哪一层。不要只在表层的交互代码里一层层堆补丁。

## 文档阶段状态

路线图、架构文档和阶段清单都要用下面这套状态标记：

| 状态 | 标记 | 含义 |
|------|------|------|
| 已完成 | ✅ | 已经交付，并且通过了验证 |
| 警告 | ⚠️ | 有风险、有偏差，或者还有问题没处理；只实现了一部分、没做专项手工测试的，也标这个 |
| 暂缓 | 💤 | 在计划范围内，但实现起来太难，暂时决定不做 |
| 延期 | ⏭️ | 在计划范围内，但已经推迟，必须注明原因和新的目标时间 |
| 未开始 | ❌ | 还没有启动 |
| 放弃 | 🚫 | 已经决定不做，必须注明原因 |

## 执行约束

- 要加新功能，先确认它属于哪个阶段、当前是什么状态。标着「未开始」或者「放弃」的条目，不许自己动手开工。
- 干完一件事，把对应的文档条目改成 ✅；如果发现实现和计划有偏差，标成 ⚠️ 并写清楚问题在哪。
- 阶段延期或者范围被放弃时，必须更新状态标记并记下原因，不许不声不响地搁着。
- 用户报 Bug 或者反映行为不对时，先建议切到 Debug 模式，不许做没有证据支撑的试探性修改。

## 计划文档（.plan）

- `.plan/` 目录专门放计划文档。
- 进入 Plan 模式后的第一件事，就是把这份计划文档同步一份到 `.plan/`。
- 计划文档要能表示功能做到了什么程度，写成带状态的清单，可以有子项和前置依赖。可以把它理解成一份控制力更强的待办表。
- 计划文档在实现过程中可以随时改，开发中发现的新问题也可以往里插。
- 命名格式：`x年-x月-x日-?-小标题.md`，其中 `?` 用 emoji 表示实现状态。

## 严重缺陷记录（.bugfix-reports）

不是所有 Bug 都要写记录，只有严重的才写。

- 写下来的目的是让 AI 能回顾以前踩过的坑，不要在同一个地方反复摔。
- 目录：`.bugfix-reports/`。
- 命名格式与计划文档一致：`x年-x月-x日-?-小标题.md`。
