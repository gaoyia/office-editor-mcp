# 工程原则

本项目是全新实现，所有修改一律不考虑旧版兼容问题。

## 核心信条

1. **质量优先，架构优先**：重大变更先定边界、模块职责与依赖关系，遇到跨模块行为、性能问题或系统边界问题时，先建立顶层设计和数据流判断，再写实现代码。
2. **不留技术债**：不用临时 workaround 掩盖真实架构债。短期修复必须清楚说明边界，并为长期正确路径保留或补齐计划。禁止「先凑合、以后再改」。临时方案须标注偿还计划与截止时间，否则拒绝合入。
3. **分阶段演进**：按阶段交付可验证的增量，每阶段有明确入口、出口与验收标准，修改应尊重现有模块边界。每个架构性变更都要配套验证：单元测试覆盖核心不变量，文档记录运行时假设，手工清单验收。
4. **文档先行，同步演进**：规格与契约以 `docs`为真源。新增或变更行为时，**先更新文档再写代码**；代码合入时文档须同批对齐。禁止无文档依据的实现，也禁止只改代码留文档债务。
5. **先计划、后实施、再验证**：严格遵循「计划 → 实施 → 验证」闭环，不得跳过任一环节。
6. 与用户对话表达有感情，符合语言语法规范，通俗易懂的表述，不要能省就省，缺字少字。

## 工作流

| 阶段 | 要求 |
|------|------|
| 计划 | 明确目标、范围、架构影响、阶段划分与验收标准；涉及契约/页面/API 时先列出待改文档 |
| 文档 | 更新对应 `docs` 确认与已决约束无冲突 |
| 实施 | 按已更新文档实现，保持最小必要改动，不引入未记录的债务 |
| 验证 | 运行测试、检查文档与实现一致，确认阶段出口条件已满足 |

复杂任务先输出计划（可切换 Plan 模式），用户确认或范围清晰后再实施。实施前确认相关文档已更新或已明确「本阶段仅改文档」。

## 缺陷处理

遇到 Bug 时，**不得**在 Agent 模式下凭猜测直接改代码。须提醒用户切换到 **Debug 模式**，基于运行时证据（日志、堆栈、复现步骤）定位根因后再修复。
性能问题先定位阻塞点、同步边界、数据拷贝和事件调度，再决定优化位置；不要只在表层交互代码里堆补丁。

## 文档阶段状态

路线图、架构文档、阶段清单须使用以下状态标记：

| 状态 | 标记 | 含义 |
|------|------|------|
| 已完成 | ✅ | 已交付并通过验证 |
| 警告 | ⚠️ | 存在风险、偏差或待处理问题 部分实现 / 未专项手测 |
| 暂缓 | 💤 | 计划内但实现困难，暂定不做 |
| 延期 | ⏭️ | 计划内但已推迟，须注明原因与新的目标时间 |
| 未开始 | ❌ | 尚未启动 |
| 放弃 | 🚫 | 已决定不做，须注明原因 |

## 执行约束

- 新增功能前，确认其归属阶段及当前状态；未开始或已放弃项不得擅自启动。
- 完成工作后，将对应文档项更新为 ✅；若发现偏差，标为 ⚠️ 并说明问题。
- 阶段延期或范围放弃时，必须更新状态标记并记录原因，不得静默搁置。
- 用户报告 Bug 或异常行为时，优先建议切换 Debug 模式，禁止未经证实的试探性修改。

## plan 计划模式

- `.plan` 目录专门存放 plan 文档。
- plan 计划模式第一步：把 plan 文档同步一份到 `.plan` 目录。
- plan 文档需实现功能完备度的状态机表示（可含子项目或前置依赖），可视为工程控制力更强的 todo。
- plan 文档在实现过程中可逐步修改，也可随开发阶段发现的新问题插入内容。
- 命名：`x年-x月-x日-?-小标题.md`（emoji 表示实现状态）。

## 严重 Bug 修复记录（强调：不是所有 Bug 都严重）

- 该目录文档便于 AI 总结既往经验，避免反复踩同一问题。
- 目录：`.bugfix-reports`
- 命名同样为 `x年-x月-x日-?-小标题.md`。
